# 共笔：可由用户定义的 AI 协作环境

日期：2026-10-11。状态：Q1–Q19 产品决定已逐项确认，本合并稿待用户核对整体理解。本方案的应用实现尚未开始。

访谈与代码依据见 [产品重审记录](product-realignment-2026-10-11.md)。术语见 [GLOSSARY.md](../GLOSSARY.md)。本文区分用户已确认的要求与工程建议。

## 1. 产品定位

共笔是以本地 Markdown 和开放接口为基础、支持用户定义多种 AI 协作方式的通用产品。用户根据任务选择交互模式，也能在软件内部用自然语言让 Agent 创建、修改模式，体验预览后再使用；外部 Agent 同样可依据文档接入。

模式可以同时定义工作区前端、交互流程和 Agent 行为，包括主动程度。模式作者可调用产品提供的模组，也可自行实现相应体验。产品不强制所有模式采用相同的页面布局、按钮、运行提示或修改处理界面。

模式与文件独立，可在不同笔记库中复用。同一份资料可采用不同模式。现有三栏界面及入口没有必须保留的约束。

## 2. 页面自适应

系统工作区应根据模式和正在发生的互动调整功能组织。仅换颜色、提示词、标题或移动聊天面板，不满足用户要求。

模式可以提供可复用的阶段页面；Agent 在运行中也能根据当前需要临时生成新的交互界面。例如学习函数时生成可拖动参数的曲线演示，直接放入当前学习过程。用户正在输入或作答的区域应保持稳定。

这意味着需要支持两种创作活动：

- **修改模式**：调整可复用的界面与行为，先在可操作的预览中迭代。
- **运行中的生成**：围绕当前交流创建适用的交互内容，无需先返回模式编辑器。

二者何时互相转化，例如把本次生成的演示保存成可复用模组，属于后续设计点，不能默认为每次生成都永久改动模式。

## 3. 三种默认模式

| 模式 | 已确认的主要过程 | 用于原型验证的页面组织建议 |
|---|---|---|
| 自由共写 | 围绕资料讨论、修改笔记，按需生成 MD 或 HTML | 根据当前工作展示资料、正文、局部讨论或成果视图 |
| 自适应学习 | 用户提出主题 → 问题判断认知范围 → 确定学习范围 → 讲解知识点 → 小测检验、加深记忆 | 诊断时突出问题与回答；规划时展示学习内容；讲解时可加入图解与演示；小测时突出作答和反馈 |
| 资料整理 | 读取多份材料 → 提出整理方案 → 执行用户选定的操作 | 材料对照、方案选择、受影响文件及执行结果随阶段展开 |

页面组织是具体化建议；默认模式应通过同一组开放能力构建，并允许用户修改。平台仍须支持用户创造其他模式。

自适应学习可以跨聊天参考同一主题的回答、小测与薄弱点；允许用户从头开始或纠正此前判断，旧记录不作为永久能力结论。

## 4. 记录、模式切换与正在运行的 Agent

- 交流过程像聊天历史一样保留，不要求引入项目看板或重型任务管理。
- 同一条交互记录中切换模式，承接已有历史，后续交互采用新模式的规则。
- 已经运行的一轮继续按原模式完成，切换不打断此前的 Agent 行为；用户仍可主动停止。
- 记录的保存与当前页面形态是不同要求。当前页面可以呈现问题、演示、编辑器或资料对照，不必始终采用聊天气泡布局。

工程上需要让正在运行的 Agent 与页面的挂载、卸载相互独立，并保留结果归属。应用关闭后的后台运行、崩溃恢复、多 Agent 并发调度尚未被这项决定覆盖。

## 5. 文件与展示格式

- 保留本地 Markdown 及开放性。
- 用户可描述希望的 HTML 风格，让 Agent 从 MD 按需生成 HTML；也可从 HTML 转换为 MD。
- 不要求每篇笔记都预先保存两种格式。
- 格式之间保留来源关系，后续默认由用户提出要求再更新；自动更新可以配置。
- 可在 Type 栏切换 MD/HTML，入口可显示或隐藏。只有 Markdown 需求的用户无需看到冗余入口。

这里确认的是按需转换和更新，不是所有视图都必须实现逐字段、实时、双向绑定。HTML 转为 MD 时对布局和交互的保留范围需要在工程方案中说明，不能承诺无损转换。

## 6. 模式创建体验

已确认的过程是：用户描述想要的模式 → Agent 利用产品上下文编写 → 用户在可操作的预览中体验并提出调整 → 使用该模式。

供 Agent 使用的上下文应说明产品是什么、已有能力有哪些、怎样编写及运行代码。为使这个过程可验证，建议提供以下工程材料：

- 可调用的能力及其输入、输出说明。
- 可复用模组的目录、示例与替换方式。
- 可运行的最小模式示例。
- 运行、预览和错误诊断入口。

上述材料是工程建议，具体文件格式和 API 名称尚未确定。外部 Agent 与软件内 Agent 应能依据公开文档完成同类扩展。

## 7. 从当前实现到目标的主要工作

初次审计已确认的基础包括本地文件、原生编辑器、CLI Agent、命令层、提案、问答、HTML 模块和插件。它们可作为实现起点。

| 当前边界 | 需要满足的目标 |
|---|---|
| 主工作区的几个页面分支写在宿主代码中 | 模式能定义界面组合与互动过程，运行中可呈现新生成界面 |
| 空间规则依据笔记所属文件夹选取 | 模式独立选择并跨资料、跨库复用 |
| 内置问答逻辑与 Agent 侧栏的固定卡片耦合 | 等待和回传答案的能力可供自定义界面使用 |
| HTML 命令桥缺少可用的 Agent 持续事件订阅 | 自定义界面能够获得运行进度、结果和交互状态 |
| 会话与部分交互状态集中在当前应用对象中 | 历史、模式选择、页面状态及正在执行的一轮具有清晰归属 |
| 既有 HTML 开关仅切换同一文件的源码/预览 | 形成按需格式转换、来源关联和可选 Type 入口的完整体验 |

以上是目标差距，不代表技术栈、存储结构和实现细节已确定。最新源码需要在正式实施前再次核对；本轮访谈期间未修改应用源代码。

## 8. 可体验的验收场景

以下是从已确认要求推导的验收草案，供整体核对和原型使用。

| 场景 | 验收结果 |
|---|---|
| Agent 创建一种新模式 | 根据产品文档，调用可选模组或自写界面，做出可操作预览；无需为该模式新增宿主专属页面分支 |
| 同一份资料使用不同模式 | 文件保持原处，交互方式和页面功能随模式变化；同一记录的历史仍可使用 |
| 旧 Agent 运行期间换模式 | 原来的运行继续，结果没有丢失，新模式可以用于后续交互 |
| 自适应学习完整过程 | 从诊断、定范围、讲解到小测的界面与行为真实变化；回答能够影响后续学习 |
| 运行时生成演示 | Agent 根据当前学习需要加入可实际操作的界面，其交互能参与学习过程 |
| 隔天新聊天继续主题 | 可参考旧学习记录，也可从头开始或纠正判断 |
| MD 转 HTML 后修改 MD | 原 HTML 默认不被后台重写；提出更新要求后可依据来源更新并尽量保留展示风格 |
| 纯 Markdown 用户 | 可以隐藏格式切换入口，不被要求生成 HTML |
| 跨笔记库使用模式 | 模式可复用，不与某一份文件或文件夹一对一绑定 |

## 9. 建议实施顺序与未定工程细节

建议先做能检验上述验收场景的最小端到端原型，优先验证“Agent 可定义、工作区真实变化、历史承接、运行不被切换中断”。再扩大模组和默认模式的完整度，最后系统打磨性能与动效。基础交互卡顿或布局问题若阻碍原型体验，应同步修复。

下一阶段需要给出并验证的工程选择包括：扩展运行环境、模组与事件协议、记录持久化、版本更新、生成界面的保存与复用、跨库配置、并发写入和格式来源关联。它们不能被描述为用户已选择的具体实现；低层实现可由工程判断提出，涉及改变上述产品行为或引入明显使用限制时需单独说明。

本合并稿的确认只用于核对产品理解。正式实现的范围、原型交付形式与验证方式应在开始时明确。
