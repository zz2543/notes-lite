监视测试只等可观察结果：先反复写隐藏探针文件直到监视器报告（应对 FSEvents 启动延迟及迟到的建库事件），之后每一步都等到路径被报告为止，不用固定等待。

实施中的决定：
- 核心库 `watchLibrary` 用 Node 自带的递归 `fs.watch`（macOS FSEvents、Windows ReadDirectoryChangesW），不加依赖。路径一律相对笔记库、以 `/` 分隔，含隐藏路径（供以后的空间主页用），“”表示任何地方都可能变了。首个事件后 80 ms 内的变化合并为一次通知，每个路径只报一次。应用自己保存时的 `.<名>.<pid>.saving` 临时文件不报告，但保存本身照常报告（空间规格要求三种来源都触发）。Windows 上笔记库文件夹被删时 `fs.watch` 会报错，已处理为一次“全部可能变化”的通知，不会让主进程崩溃。
- 界面只关心可见路径；每个文件夹视图在变化能影响它的列表时重新读取（直属条目、子文件夹是否还有子文件夹、自身或祖先），不整体刷新。选中的文件夹被移走或删除时，退到最近仍存在的上级。
- 打开的笔记：读磁盘前先等自己的写入结束（并用写入计数排除读写重叠），避免把自己的保存当成外部修改。无未保存内容时用磁盘版本替换编辑器内容（新的撤销历史，保留光标、滚动与焦点）；笔记被删或移走则关闭它并提示原因。
- 有未保存内容（包括拼音组合中）时进入保存冲突：卡片顶部出现提示，可选“保留输入”（收起提示，继续编辑，不写入）、“另存副本”（输入写成同文件夹下的“<标题> 副本.md”，编号不覆盖；文件夹也没了则放在笔记库根目录，然后打开副本）、“重新载入…”（确认后用磁盘版本替换输入）；笔记已不在磁盘上时第三项为“放弃输入…”。页脚“保存冲突”带“重试”，磁盘仍不同则再次提示。冲突期间输入不再触发自动保存；磁盘回到输入所基于的版本时自动恢复保存；磁盘内容恰好等于输入时直接视为已保存。
- 核心库新增错误码 `not-found`：笔记或文件夹已不存在时读写都给出“找不到“…”，它可能已在别处移动或删除。”，保存不写入任何东西。
- 冲突消息不再自带“你的输入仍保留在编辑器中”，由提示和切换失败的通知各自补上，避免重复。
- 监视通知同时交给任务 06 的搜索索引逐路径更新，外部修改后搜索结果跟着变。

留给后续任务：冲突提示与确认框的最终视觉与动效（浮现预设、玻璃材质）由任务 03/23 打磨；目前只用现有变量。移动笔记后编辑器不跟随到新位置（监视无法可靠配对改名），按删除处理。
